# 등급 기반 접근 제어 (오전 미니 실습)

카페 회원 등급에 빗대어, 게시판 사용자를 세 등급으로 나누고 등급별로 페이지 접근을
막는 실습이다. 목적은 **접근 제어가 실제로 동작하는지 확인**하는 것이다.

| 등급 | 값 | 설명 | 접근 가능 |
|---|---|---|---|
| 일반 | `0` | 최초 가입 상태 | `/`, `/dashboard`, `/public-post` |
| 골드 | `1` | 중간 관리자 | 위 + `/gold` |
| 관리자 | `2` | 전체 관리 | 위 + `/admin` |

등급은 **숫자가 클수록 권한이 넓다**. 그래서 검사는 `user.role >= 요구등급` 한 줄로 끝나고,
관리자는 골드 페이지도 자동으로 볼 수 있다.

---

## 1. 설계에서 정한 것

### 인가는 서버에서 한다

이 프로젝트는 JWT를 `localStorage`에 두고 JS가 `Authorization` 헤더로 보내는 구조였다.
이대로면 페이지 접근 제어를 JS로만 할 수밖에 없는데, 그건 **링크를 숨기는 것**일 뿐
주소창에 `/admin`을 직접 치면 그대로 열린다. 즉 접근 제어가 아니다.

그래서 로그인할 때 JWT를 **쿠키로도 발급**한다. 브라우저 주소창 이동(GET)에도 토큰이
실리므로, 서버가 페이지를 그리기 전에 등급을 확인하고 거절할 수 있다.

```
로그인 → JWT 발급 → ① 응답 본문(localStorage용, 기존 fetch API가 사용)
                  → ② Set-Cookie (페이지 이동 시 서버가 등급 판정)
```

기존 API 호출은 헤더 방식 그대로라 아무것도 깨지지 않는다.

### CSRF 보호는 켜 둔다

쿠키 인증을 붙이면 CSRF가 따라온다. `JWT_COOKIE_CSRF_PROTECT = True`로 두었다.

- 페이지 라우트는 GET이라 CSRF 검사 대상이 아니다 → 영향 없음
- 변경 API(`PATCH`/`DELETE`)는 헤더 토큰을 쓴다 → 영향 없음
- 관리자 화면은 안전하게 `X-CSRF-TOKEN` 헤더도 함께 보낸다

### 화면 표시와 인가 판정의 출처를 하나로 맞춘다

헤더의 유저명·등급 배지는 `localStorage`가 아니라 **서버가 렌더링**한다.
화면에 보이는 등급과 실제로 접근을 판정하는 값이 둘 다 DB의 `users.role`에서 나오므로,
"화면엔 골드인데 실제론 막힌다" 같은 어긋남이 생기지 않는다.

## 2. 구현 구조

```
models/user.py                 role 컬럼(0/1/2), ROLE_* 상수, has_role()
controllers/authz.py           인가 도구 — 여기가 접근 제어의 핵심
controllers/auth_controller.py 가입(항상 0) / 로그인(쿠키 발급) / 로그아웃 / /me
controllers/admin_controller.py 회원 조회·등급 수정·삭제 API
controllers/page_controller.py /gold, /admin 라우트 + 템플릿 컨텍스트
templates/gold.html            골드 전용 화면
templates/admin.html           관리자 회원 관리 화면
templates/403.html             접근 거부 예외 화면
templates/partials/_nav.html   등급별 헤더 링크 + 유저명·권한 표기
scripts/manage_roles.py        role 컬럼 추가 / 등급 지정 CLI
tests/test_authz.py            접근 제어 테스트 23개
```

### 인가 검사 한 곳 (`controllers/authz.py`)

```python
def api_role_required(required_role):   # JSON API용  → 401/403 JSON
def page_role_required(required_role):  # 페이지용    → 401/403 예외 화면
```

두 데코레이터 모두 같은 판정을 쓰고, 응답 형식만 다르다.

- **로그인 안 됨 → 401** (인증 실패)
- **로그인은 됐지만 등급 부족 → 403** (인가 실패)

이 둘을 섞지 않은 이유는, 화면에서 원인을 바로 구분하기 위해서다.
401은 "로그인하세요", 403은 "등급이 모자랍니다"로 안내가 달라진다.

### 라우트에 붙이는 법

```python
@page_bp.get("/gold")
@gold_page_required          # 골드(1) 이상
def gold_lounge(): ...

@page_bp.get("/admin")
@admin_page_required         # 관리자(2)만
def admin_console(): ...

@admin_bp.get("/users")
@api_role_required(ROLE_ADMIN)
def list_users(): ...
```

## 3. API

| 메서드 | 경로 | 요구 등급 | 설명 |
|---|---|---|---|
| POST | `/api/auth/register` | - | 가입. **항상 일반(0)**, 본문의 `role`은 무시 |
| POST | `/api/auth/login` | - | 로그인. 토큰 + 쿠키 발급, 등급 반환 |
| POST | `/api/auth/logout` | - | 쿠키 삭제 |
| GET | `/api/auth/me` | - | 현재 로그인 상태와 등급 |
| GET | `/api/admin/users` | 관리자 | 회원 목록(등급·게시글 수) |
| PATCH | `/api/admin/users/<id>` | 관리자 | 등급 수정 |
| DELETE | `/api/admin/users/<id>` | 관리자 | 회원 삭제(게시글 함께 삭제) |
| PUT | `/api/posts/<id>` | 작성자 본인 | 게시글 수정 (관리자도 남의 글은 못 고침) |
| DELETE | `/api/posts/<id>` | 작성자 본인 **또는 관리자** | 게시글 삭제 |

### 게시글 삭제 권한

관리자에게는 **삭제만** 열어 주고 수정은 열지 않았다. 부적절한 글을 내리는 것과
남의 글 내용을 바꾸는 것은 성격이 다르기 때문이다. 후자는 작성자 몰래 발언을
바꾸는 셈이라, 중재 권한의 범위를 넘는다고 판단했다.

관리자가 남의 글을 지우면 응답에 `moderated: true`가 실리고, 화면에도
「관리자 권한으로 ○○님의 글을 삭제했습니다」라고 알려 준다. 본인이 지운 경우와
구분해서 남기기 위한 것이다. 게시판 목록에서도 남의 글에는 일반 `삭제`가 아니라
테두리가 있는 **`관리자 삭제`** 버튼으로 표시된다.

### 안전장치

관리자 자신이 관리 화면에서 잠기는 사고를 막는다.

- 자기 자신의 등급을 내릴 수 없다
- 자기 자신을 삭제할 수 없다
- 마지막 남은 관리자는 강등·삭제할 수 없다
- `role` 값이 0/1/2가 아니면 400

## 4. 실행 방법

기존 `users` 테이블에는 `role` 컬럼이 없다. `db.create_all()`은 이미 있는 테이블에
컬럼을 추가하지 못하므로 **한 번만** 아래를 실행한다.

```bash
python scripts/manage_roles.py --ensure-column
```

계정을 만들고 등급을 준다. 가입은 화면에서 해도 되고 아래처럼 해도 된다.

```bash
python scripts/manage_roles.py --promote gold01 --role 1
python scripts/manage_roles.py --promote admin01 --role 2
python scripts/manage_roles.py --list
```

서버 실행:

```bash
python app.py
```

## 5. 제출 증거 캡처 순서

아래 순서대로 캡처하면 요구사항 6개가 모두 화면에 남는다.
데모 계정은 `normal01`(0) / `gold01`(1) / `admin01`(2), 비밀번호는 모두 `pw1234`.

### 증거 1 — DB의 등급 값

```bash
python scripts/manage_roles.py --list
```

터미널에 `id / 등급 / 아이디`가 찍힌 화면을 캡처한다.
(MySQL에서 직접 보려면 `SELECT id, username, role FROM users;`)

### 증거 2 — 로그인 시 헤더에 유저명 + 권한 표기

세 계정으로 각각 로그인하고 **헤더 우측**을 캡처한다.

| 계정 | 헤더에 보여야 하는 것 |
|---|---|
| `normal01` | `normal01님` `일반 (0)` — 골드/관리자 링크 **없음** |
| `gold01` | `gold01님` `골드 (1)` — `☕ 골드 라운지` 링크 **있음** |
| `admin01` | `admin01님` `관리자 (2)` — 골드 + `🛠️ 관리자` 링크 **둘 다 있음** |

### 증거 3 — 접속 시도와 결과 화면

| 로그인 상태 | 접속 주소 | 결과 |
|---|---|---|
| 비로그인 | `/admin` | **HTTP 401** 「로그인이 필요합니다」 |
| `normal01` (0) | `/gold` | **HTTP 403** 「접근 권한이 없습니다 · 현재 등급은 일반입니다」 |
| `normal01` (0) | `/admin` | **HTTP 403** 요구 관리자(2) / 내 등급 일반(0) |
| `gold01` (1) | `/gold` | **정상** 골드 라운지 |
| `gold01` (1) | `/admin` | **HTTP 403** 요구 관리자(2) / 내 등급 골드(1) |
| `admin01` (2) | `/gold` | **정상** (상위 등급은 하위 페이지 포함) |
| `admin01` (2) | `/admin` | **정상** 회원 관리 |

> 예외 화면에는 **요구 등급**과 **내 등급**이 나란히 표시되므로,
> 이 캡처 한 장으로 "왜 막혔는지"까지 함께 증거가 된다.

핵심 캡처는 **헤더 링크가 안 보이는 상태에서 URL을 직접 입력해도 막히는 화면**이다.
링크 숨김이 아니라 서버가 막고 있다는 증거다.

### 증거 4 — 관리자 회원 관리

`admin01`로 `/admin` 접속 후:

1. 회원 목록에 아이디·현재 등급·게시글 수가 나오는 화면
2. `normal01`의 등급을 `골드 (1)`로 바꾸고 **저장** → 상단 초록 안내문
   「normal01님의 등급을 일반 → 골드(으)로 변경했습니다.」
3. 승급된 계정으로 다시 로그인 → 아까 403이던 `/gold`가 **열리는** 화면
4. 회원 삭제 → 「gold01님을 삭제했습니다. (게시글 N건 함께 삭제)」
5. 안전장치: 자기 자신 등급을 `일반 (0)`으로 바꿔 저장 → 빨간 안내문
   「자기 자신의 등급은 내릴 수 없습니다.」

### 증거 5 — 관리자의 게시글 삭제

1. `normal01`로 로그인해 글을 하나 쓴다 → 본인 글이라 `수정` `삭제`가 보인다
2. `admin01`로 로그인해 같은 글을 본다 → **`관리자 삭제`** 버튼만 보이고
   `수정`은 없다 (남의 글은 고칠 수 없다)
3. `관리자 삭제` 클릭 → 확인창
   「관리자 권한으로 normal01님의 글을 삭제합니다. 계속할까요?」
4. 확인 후 안내
   「관리자 권한으로 normal01님의 글을 삭제했습니다.」
5. `gold01`로 로그인해 남의 글을 보면 삭제 버튼 자체가 없다
   (API를 직접 호출해도 403)

## 6. 테스트

```bash
python -m pytest tests -q
```

`tests/test_authz.py`가 접근 제어를 검증한다.

- 가입은 항상 일반(0)이고, 본문에 `role: 2`를 넣어도 무시된다
- 비로그인/일반/골드/관리자별로 `/gold`, `/admin` 응답 코드가 401·403·200으로 갈린다
- 헤더에 유저명과 등급이 함께 렌더링된다
- 링크가 숨겨져도 URL 직접 입력은 서버가 막는다
- 승급 전 403 → 승급 후 200으로 바뀐다
- 관리자 안전장치(자기 강등·자기 삭제·마지막 관리자)가 모두 거절된다
- 관리자는 남의 글을 삭제할 수 있고, 일반·골드는 403으로 거절된다
- 관리자도 남의 글 **수정**은 403으로 거절된다
- 로그아웃하면 페이지 접근이 다시 막힌다

## 7. 남는 한계 (실습 범위 밖)

- 등급 변경 이력을 남기지 않는다. 누가 언제 누구를 승급했는지 추적하려면
  `SecurityEvent`에 기록을 붙이는 게 자연스럽다.
- 게시글 **수정**은 작성자 본인만 가능하다. 관리자도 남의 글 내용은 고칠 수 없다.
- 관리자가 지운 글은 복구할 수 없다. 실제 서비스라면 바로 지우지 말고
  `deleted_at`을 찍어 두는 소프트 삭제가 안전하다.
- 토큰 만료(2시간) 전에 등급을 내려도 쿠키는 살아 있다. 다만 인가 판정은
  매 요청 DB의 `users.role`을 다시 읽으므로 **강등은 즉시 반영된다.**
